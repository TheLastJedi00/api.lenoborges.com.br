# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

`eduleno-back` is a NestJS 11 backend on Firebase (spec 007, which replaced Supabase). Firestore holds business data (`waitlist_entries`, `profiles`); Firebase Auth handles identity. Both go through `firebase-admin` with a single service account, confined to `FirebaseService`. The project follows a simple MVC layout with modules, controllers, services, and repositories. Repositories always return objects `{ found, entry }`, never primitive `null` directly — that boundary is what let the Postgres-to-Firestore swap land in two classes without touching a service.

**There is no schema and no migrations.** Firestore has no DDL, so guarantees that used to live in the database now live in code, and they are easy to lose by accident:

- **Document IDs carry meaning.** `waitlist_entries/{normalized-email}` is how email uniqueness is enforced — Firestore has no `UNIQUE` constraint, and the document path is the only place it guarantees uniqueness. `profiles/{firebase-uid}` replaces the old FK to `auth.users`. Never switch these to auto-IDs plus a query.
- **`create()`, never `set()`** in the repositories: `set()` overwrites silently, and it is the `ALREADY_EXISTS` from `create()` that stands in for the Postgres `23505` unique violation.
- Value ranges (`grade` 0–13; see spec 008 (Liga Dev), which lives in the **front** repo — 1-8 are badges, 9-12 the Elite Four, 13 post-game) and required fields are validated in the application; `firestore.rules` denies everything, since only the Admin SDK — which bypasses rules — touches the data.
- **`badge_videos/{badgeId}__{youtubeId}`** (spec 009) is the same idea applied twice: the composite path is what keeps a video from entering the same badge twice, while still allowing it in a different badge. And `order` is **renormalized to 0..n-1 inside an atomic `WriteBatch`** on every reorder and delete — a per-video update leaves two videos on `order: 3` when the second write fails, and that list is wrong in silence.
- **The badge listing is the first query that is not by path**, so it needs a composite index (`badgeId` + `order`) in production. The emulator does not require indexes, so the suite stays green and the failure only shows up live.
- **`extractYoutubeId` owns YouTube URL normalization, and the list of forms it knows is the whole list the product accepts** (specs 009, 017). Six forms — `watch?v=`, `youtu.be/`, `/embed/`, `/shorts/`, `&t=`, `?si=` — normalized **once, on the way in**, so what gets stored is always the 11-character ID. A form that is not in that function is a `400` in the admin's face, and that is exactly how the answer-video feature shipped broken: spec 010 created the Perguntas Frequentes tab, the answer video is a Short, and `/shorts/` was not in the list until spec 017 — the feature looked finished and refused the only link the YouTube app copies on a phone. **Shorts needs nothing beyond the extraction**: same ID, and the embed player serves a Short with no special handling. Do not go looking for a Shorts player; the only thing that differs on screen is the iframe ratio, and that comes from the derived `orientation`.
- **A `BadgeVideo` of kind `resposta` carries a photograph of the question, not a join** (spec 017). `question: { id, title, authorName, askedAt }` is written once, at publish time, for three reasons that stack: a join would cost one extra read *per listing* instead of one per video; the admin can delete a mural question and the published video stays up, so a join would erase the balloon and leave an orphan video; and the author can edit the question while it is in `coleta` (spec 016), so the photo is what was actually asked. **Editing the question later does not change the balloon, and that is the intended behavior.** `askedAt` is the question's `createdAt`, never the video's. Publishing an answer also writes `answerVideoId` back onto the question — the field that had existed since spec 010 with nothing ever writing it — **last, and in a swallowing `catch`**, because by then the video is live and the student's balloon comes from the photo, not from that pointer.
- **`orientation` is derived in `toDto` and never stored** (spec 017), the same shape as the Mural's `phase`: `resposta` is `retrato` (9:16), `aula` is `paisagem`. Deriving it from `kind` on the front would put one product rule in a template, a stylesheet and a test, and each would age on its own — the point of the server owning it is that the day an answer is shot in landscape, one line changes here and no front is deployed.
- **`role` is a Firebase Auth custom claim, never a Firestore field** — it rides inside the ID token the guard already verifies. It takes effect only on the *next* token, up to an hour later (`CHECK_REVOKED = false`). Granting is `npm run admin:grant -- <email>`; there is no endpoint that creates an admin.
- **The Mural's weekly rollover is a computation, not a cron** (spec 010). Each question stores the `weekId` it was born in, and its phase is derived at read time from the server clock in `America/Sao_Paulo`. A cron that fails to run would freeze the board on last Sunday — silently, with no error, until a student notices. Never replace this with a scheduled job.
- **The Mural's promotion is a floor, never a state** (spec 016). `promotedTo` raises the bottom of a question's phase — `fase = max(clock, promotedTo ?? 'coleta')` — and never holds the ceiling, so **the clock still wins whenever it is ahead** and no question can be stuck in a stale phase. A stored `status` would have exactly the failure the spec 010 cron avoided, minus the cron: someone promotes, the week passes, the document still says `votacao`, and the board shows a three-week-old question in voting. No error, no alarm, and the first person to notice is a student. The same one function answers "what phase is this in" — `phaseOf(question, now)` — and its signature was changed on purpose, so the compiler pointed at all three callers instead of leaving one reading the old phase.
- **The cut of promoted questions is in memory, and `where('promotedTo', '==', null)` is the trap** (spec 016). In Firestore, `== null` matches a document where the field **exists and is null**, and not one where the field is absent — and every question written before spec 016 is absent. `findWinner` therefore loads the week through `listByWeek` and picks in memory; the query would return an empty winner history for every earlier week, with no error and a 200. The same read hands the pauta its promoted questions, so the two origins cost no extra query and no new index — and the index table in `README.md` gains no row from this spec.
- **`tier` is a Firestore field while `role` is a claim**, and the difference is deliberate: tier changes often and must take effect immediately, while a claim would take up to an hour. `tier` is *access*; `grade` is *achievement* — neither derives from the other, in either direction.
- **Subcollections do not disappear with their parent** in Firestore. Deleting a mural question deletes its `votes` subcollection explicitly, or the votes are orphaned — invisible, billed, and unfindable.
- **`notifications/{video__badgeId__youtubeId | pergunta__questionId}`** (spec 012) is the same path-as-uniqueness rule again: a retried publish cannot announce the same video twice. Notifications are **global, one document per event — never fanned out per member**, and what is per-person is only what they have read, in `profiles/{uid}/notification_reads/{notificationId}`. That subcollection is the one place where **`set()` is right and `create()` would be wrong**: marking as read has two callers in the panel and must be idempotent. It is also a subcollection, so deleting a profile has to delete it explicitly — same trap as the mural votes.
- **Writing a notification never decides the fate of the thing it announces** (spec 012). The video is created, the question is written, and only then the notification goes out — outside the try that translates `ALREADY_EXISTS`, with a `catch` of its own at each trigger. That `catch` looks like carelessness and is the decision: a 500 there would lose the admin's work over an advisory. Failures log; they never surface.
- **Four queries need composite indexes in production** — two on `mural_questions` (week+votes+created, week+created) and two on `badge_videos` (badge+order, badge+kind+order). Note the pair on `badge_videos`: `kind` is optional in `listByBadge`, so badge+order is a real query and not a prefix of the other one. The emulator does not require indexes, so the suite stays green and the failure only shows up live. **The count belongs in the README table, not in this sentence** — it has already gone stale twice. See "Índices compostos que produção exige" in `README.md`.
- **Deleting an account anonymizes what belongs to the community and erases what belongs to the person** (spec 013). The Firebase Auth user, `profiles/{uid}`, its `notification_reads` subcollection, the votes cast, and the waitlist entry are erased; the person's mural questions survive with `authorUid: '__removido__'` and `authorName: 'Membro removido'`, because they carry other people's votes and may already answer a track video. **The Auth user dies last** — there is no transaction spanning Firestore and Firebase Auth, so the only choice is which half survives a mid-way failure, and Auth-first would leave orphaned personal data with nobody entitled to ask for its removal. The whole thing is anonymization rather than pseudonymization on **one condition: no new collection may store `uid` alongside personal data** — a persistent log with uid and email together re-links the orphan identifier. That condition is written next to `ANONYMOUS_AUTHOR_UID` in `mural-question.entity.ts`, where whoever breaks it will read it.
- **Password is the proof of ownership, never the token** (spec 013). `POST /me/email`, `POST /me/password` and `DELETE /me` all re-authenticate through `AuthService.reauthenticate`, which hits the same `accounts:signInWithPassword` as login — a stolen ID token is good for an hour, and an hour is enough to take the account for good. There is exactly **one** place that can say "this password is correct"; a second one would diverge on the first exception. `POST /me/email` **does not change the email** — it asks the Identity Toolkit for a `VERIFY_AND_CHANGE_EMAIL` code sent **to the new address**, and Google performs the swap on the click.

- **The unsubscribe is absolute, and there is no configurable exception** (spec 014). No email this code sends — automatic, manual, or a future "important notice" — skips `emailOptOut`. The legitimate exception, account email (password reset, address verification), never passes through here: Firebase sends those, by another path (spec 007). **That separation is what lets the rule be absolute without hurting anyone**, and it is also why manual and automatic sends share one `EmailCampaignService.send` — two send paths would mean the automatic one forgets the opt-out, because whoever writes a trigger is not thinking about lists.
- **The campaign cursor is what prevents resending from the start, and the `uid` ordering is what sustains it** (spec 014). The audience is sorted by `uid`, sent in batches of 100, and `cursorUid` is written after each batch — so a function that dies on batch seven leaves the campaign `interrompida` with the cursor at the end of batch six, and "Resume" continues from there. Change that ordering to anything else and resuming restarts from an arbitrary point: some people get it twice, others never. **A batch may duplicate and that is accepted**: duplicating one email for a hundred people is an annoyance; losing the send for the other thousand is the feature not working.
- **The admin list is a full scan of Auth, sliced in memory — not a page** (spec 015). `GET /admin/users` walks `listUsers` to the end, joins `profiles` by path, and only then applies search, filters, ordering and the page. The reason is not performance, it is correctness: **the person the "onboarding pendente" filter looks for is the one with no Firestore document**, so filtering a page would return whichever pending members happened to land in the first 50 uids, and the screen would say "3 membros" with complete confidence. The join has exactly one owner, `MemberDirectoryService`; the admin list and the email audience both call it, and two implementations of the same join diverge on the first new profile field. There is deliberately **no cache** — serverless means per-instance, and the first symptom would be a tier edit that reappears old on reload, in some requests and not others.
- **`recipientUid` is read before the campaign filters, and that order is what keeps a message to one person from becoming a blast to everyone** (spec 015). A `direto` campaign stores `filters` with all three fields null, and null filters mean *all members* — so `buildAudience` checks `recipientUid` first and returns a single recipient; the filters are only consulted when it is null. It has its own trap test, and the comment above the `if` says what the test prevents: without it, the next "simplification" of the condition order turns a personal note into a send to the whole base. The same care applies in the converter — `recipientUid ?? null`, because `undefined` makes an old direct campaign look like a base campaign.
- **Without `RESEND_API_KEY` the mailer logs and does not send**, and that default exists to protect production from a development machine (spec 014). The danger is not the email that fails to go out — it is the one that does: a local machine pointed at production Firestore, a test running the video trigger, and the whole base receives it. In production the boot requires the key, along with `RESEND_WEBHOOK_SECRET` and `API_PUBLIC_URL` (without the last one every unsubscribe link points at localhost, and someone who cannot leave the list presses "report spam" instead).
- **The email template is the cheapest suspect to accuse and the most expensive to convict** (spec 014). `renderEmail` emits a laid-out HTML email — a layout `<table>`, a white card, the "Liga Dev" label, an `<h1>` with the subject, a solid CTA button, and the unsubscribe footer — plus the plain-text alternative from the same source. The Promoções-tab hunt stripped that markup **twice** (`58c5bdb`, `f3be226`) and put it back twice, because removing style never breaks anything: nothing fails, the send still works, and the symptom moves or does not move for reasons elsewhere. On 2026-08-26 the other two fronts were checked end to end instead of guessed — Resend domain `verified` with `open_tracking`/`click_tracking` **off** (the real, measured cause behind `9154943`), DKIM and the `send.lenoborges.com.br` return-path SPF verified, DMARC published and relaxed-aligned, and the DNS zone at registro.br rather than Vercel, so no platform record can be pending. With provider and configuration clean, the send test was rerun and the markup did not decide the tab. **The rule that survives all three rounds: check the provider panel and the DNS before the code, and bring the measurement with you** — the template is not the last thing that happens to the email, because the provider can still rewrite the document after `renderEmail` returns. One loose end worth knowing: a stale *Tracking* `CNAME liga` sits `failed` in the Resend panel from when the tracking subdomain was not `mail`; it is inert today, but `liga.lenoborges.com.br` is the front's production domain, so it must never be allowed to verify.

Login goes through the Identity Toolkit REST API from the server, not the Admin SDK, because the Admin SDK cannot verify passwords. **Password definition happens outside this API entirely**, on Firebase's hosted screen; there is no `POST /auth/password` and the `oobCode` never reaches this code.

## Commands

```bash
npm run start:dev        # watch-mode dev server (port from PORT env var, default 3000)
npm run build            # nest build -> dist/ (deleteOutDir is on)
npm run start:prod       # node dist/main
npm run lint             # eslint over {src,apps,libs,test}/**/*.ts, autofixes
npm run format           # prettier --write over src/ and test/

npm test                 # unit tests: jest, rootDir=src, matches *.spec.ts
npm run test:cov         # coverage -> ./coverage
npm run test:e2e         # e2e: boots the Firebase emulator, runs jest --config ./test/jest-e2e.json, tears it down

# Firebase (no migrations exist — Firestore has no schema)
npm run emulators        # Auth + Firestore emulators (needs the Firebase CLI)
npm run rules:deploy     # publishes firestore.rules to the linked project
npm run admin:grant -- <email>   # grants the admin claim (add --revoke to undo)
```

**The emulator needs Java on the PATH.** Without it, `npm run test:e2e` fails at startup with "Could not spawn `java -version`" and no test runs — the unit suite (`npm test`) is unaffected.

The e2e suite runs against the emulator, never a real project. `firebase emulators:exec` sets `FIRESTORE_EMULATOR_HOST` and `FIREBASE_AUTH_EMULATOR_HOST` itself, but `FIREBASE_SERVICE_ACCOUNT_JSON` must still be present in `.env` — boot validation requires it even when the credential is never actually used against the emulator.

Run a single unit test file or case:

```bash
npm test -- app.controller.spec.ts
npm test -- -t "should return"
npm run test:e2e -- -t "/ (GET)"
```

Note the two Jest configs are separate: the inline config in `package.json` only sees `src/`, so e2e specs under `test/` will never run under `npm test`.

## Architecture

Standard Nest DI/module layout. New features follow the Nest convention of one directory per feature under `src/` containing `*.module.ts`, `*.controller.ts`, `*.service.ts`, and `*.repository.ts` (plus `dto/` and `entities/` as needed), with the feature module imported into `AppModule.imports`. `FirebaseModule` is `@Global()` and provides `FirebaseService` (Auth + Firestore) everywhere; it has to be global because `AuthModule` already imports the profile and waitlist modules, and those need Firestore — without it the dependency graph closes into a cycle.

`src/main.ts` is the only place global setup (validation pipes, CORS, Swagger, trust proxy) can be applied. Validation is strictly configured to throw on non-whitelisted properties.

## Conventions

- Prettier: single quotes, trailing commas everywhere. Prettier runs as an ESLint rule (`prettier/prettier: error`), so `npm run lint` fails on formatting violations.
- ESLint uses `recommendedTypeChecked` (type-aware). `no-explicit-any` is off; `no-floating-promises` and `no-unsafe-argument` are warnings only.
- TypeScript is deliberately loose: `strictNullChecks` on but `noImplicitAny` off and full `strict` off. Module resolution is `nodenext` with `target: ES2023`; decorator metadata is enabled (required for Nest DI).
- No path aliases are configured — use relative imports.
